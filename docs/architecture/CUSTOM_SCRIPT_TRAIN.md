# Custom mission script (`train.json`)

`train.json` is a separate HPG mission, installed in the `RANDOM AND EVERYWHERE` folder next to `everywhere_all.json`. It does not simulate anything: it sets local variables and LVARs, shows a briefing, then runs `load_mission "HEMSRandE"`. The mission reads those variables and builds the chosen incident at the chosen place. The script is independent of the mission build: it is not generated by `mission-workspace.js` and is not part of any release artifact.

## Contract between the script and the mission

| Script sets | Mission reads it in |
| --- | --- |
| `L:CUS_ID_CARD`, `L:CUS_CRASH_VARIABLE`, `L:CUS_MISSION_SCENE_VARIANT` | `CUSTOM_MISSION`, `missionupdate CUSTOM` |
| `L:CUS_ACCIDENT LAT/LON`, `L:SKIP_QUERY` | `accident location pregenerator CUSTOM` |
| `L:CUS_START` (location `START`) | reload and teleport (`reloadtemp`) |
| `L:VARAMBUAVAIL`, `L:VARFIREAVAIL`, `L:VARPOLICEAVAIL` | ground response macros (0 absent, 1 on scene, 2 on the road) |
| `L:CUS_CARLS_AUTOCONNECT`, `L:SKIPIFCLOSE`, `L:CUS_SEND_DISPATCH` | CARLS thread, dispatch hand-over |
| locals `OBJECT1..15`, `L:OBJECTn LAT/LON`, `L:CUSVFXA LAT/LON` | thread created in `accident location pregenerator CUSTOM` |
| globals of the loop over `data.accidents` (briefing text, and for ID 999 the whole definition) | `missionupdate CUSTOM` |

For every incident except 999 the mission takes the definition from its own `data.accidents`; the script copy is used only by the briefing shown before the mission loads (description of the chosen variant, objective, SAR, mountain rescuers). For ID 999 (`CUSTOM (EDITABLE)`) the script copy is the full definition and is the source of truth. The globals written by the loop match exactly the globals read by `missionupdate CUSTOM` (checked 2026-10-29).

## Version contract (2026-10-30)

| Where | What |
| --- | --- |
| Script | `L:CUS_SCRIPT_API` (contract version, now 1) and `L:CUS_SCRIPT_BUILD` (oldest mission build it needs, `major*1000+minor`, 169.87 = 169087); local `MIN_BUILD` equals the latter for the briefing. |
| Mission, `version check` | `CUS_SCRIPT_API_MIN` (oldest script API accepted, now 1) and the global `CUS_LAST_BUILD` = `BUILD_N` of the running mission, so the script briefing can warn "this script needs build X" before the mission loads. |
| Mission, `custom script compatibility` (first call of `CUSTOM_MISSION`) | API 0 or missing = original 0.997 script (legacy, accepted); API below the minimum, or `CUS_SCRIPT_BUILD` above the mission build = message for 30 s, the dispatch continues. |

Rule: raise `CUS_SCRIPT_API_MIN` in the mission and `CUS_SCRIPT_API` / `CUS_SCRIPT_BUILD` in the script (and `MIN_BUILD`) only when a mission change makes the previous script impossible. Additions that older scripts simply do not set (new optional variables) never raise it. `tools/test-custom-script.js` checks that the script API is accepted, that the script build is not newer than the mission, and that `MISSION_VERSION` stays "0.997".

Legacy script (original, frozen in `tools/fixtures/train-legacy-0.997.json`): it looks at 0.997, so `MISSION_VERSION` must stay "0.997" until 0.998, where the legacy path (numbered `OBJECT1..15` locals, `accident location pregenerator CUSTOM` fallbacks for `CUS_USERA`/`CUS_RESCUE`) and the fixture go away. The test checks that every LVAR the legacy script sets is still read by the mission. Known limit: LVARs survive between scripts in the same simulator session, so a legacy script started after a new one still reads the new `CUS_SCRIPT_API`.

## Formatting rule (user, 2026-10-30)

The formatting of `train.json` follows the layout of the original script (`tools/fixtures/train-legacy-0.997.json`), whose goal is the easiest possible reading: minimal text, delimited areas, spaces and tabs that make everything easy to find. Top-level keys in the original order with a blank line between sections, `", "` and `": "` separators, the buttons of the briefing with one command per line, the incident list one field per line. Readability pass of the same day (user: the flat layout was hard to read): in the command list the instructions are dashed banner comments in capitals (102 columns, two blank lines before the group, one after); the editable areas are opened and closed by `EDITABLE AREA STARTS/ENDS HERE` banners and their settings are indented with a tab under a short label comment; each custom object is a labelled block of aligned rows (title, lat/lon, var1/var2, aim, fallback, heading) with a blank line between objects; long commands (`for_each`, `if`) open over several lines with their `do`/`then`/`else` lists one command per line. It is not the mission formatter's layout (`mission-formatter.js`), because the file is edited by hand by users. The layout is produced by `tools/train-script-format.js` (used by the sync tool) and `tools/test-custom-script.js` fails when the file differs from it. Edit the data, then run `node tools/sync-train-accidents.js` to restore the layout.

## Keeping the incident list aligned

```
node tools/sync-train-accidents.js          rewrite the incident list of train.json
node tools/sync-train-accidents.js --check  fail if it is not aligned
```

The tool regenerates every entry except 999 from `mission-src/data/02-waypoints-and-categories.json` (fields `id`, `description1-4`, `objective`, `SAR`, `mountain_helirescuers`, `ID_CARD`), leaves the CUSTOM entry and the whole command list untouched, and formats the file with the official formatter. Run it after any change to an incident in the mission sources.

## Object engine (not finite): feasibility

Locals set by the script survive `load_mission` (the `OBJECTn` locals already rely on it), so the script can pass a list instead of numbered names. Plan:

1. The script builds one array local (for example `CUS_OBJECTS`: name, lat, lon, optional heading and state). The user edits one line per object.
2. The mission loops over the array (`for_each`) and creates location + object per item, instead of 15 copies.

Requirements fixed by the user (2026-10-29): at most 30 objects; per object a `VAR 1` and a `VAR 2` (both 0 when not given); per object an optional point_object toward a named location or object (`point_object` takes names, not coordinates); per object an optional user-chosen fallback title used when the model is missing (no fallback given means none is used; the instructions warn that fallbacks should be default objects); an optional name for the incident place, spoken and shown instead of the city.

Test: `standalone-tests/object-engine-test.json` (generated, nine buttons, each adds one piece: locations in a loop, object, title from the structure, named location reference, name and reference held in locals, VAR 1/2, point_object, fallback, 30 objects). The first failing test names the unsupported piece. Runtime pending.

Unproven, to be tested with a standalone mission in `standalone-tests/` before any mission change: (T1) a `for_each` over a local array of structures whose items give `name`, `lat`, `lon`; (T2) `create_object` with a name built from the loop counter (`param` values are thread-scoped and the production `VAR1` rule applies to drive, not to creation, but the name interpolation must be proven); (T3) the array local is still readable after `load_mission`; (T4) behaviour with 100+ objects and with a missing model. If T2 fails, the safe fallback is a generated, larger fixed number of slots (for example 60) produced by a tool, which is finite but keeps the current proven syntax.

### Implemented in the sources (2026-10-29, not built, runtime pending)

Standalone test results (simulator, Pescara threshold 04): a `for_each` over an array of structures with `create_object` works; the object name built from a counter and held in a local works; the title read from the structure works; `VAR 1` and `VAR 2` are accepted; a location created from `lat`/`lon` read from the structure is placed correctly. A location whose name was built from the counter was not proven (the engine uses one fixed name, `CUSOBJLOC`, rewritten at every object). Not proven: `point_object` on an object created in the loop, 30 objects together, an array local surviving `load_mission`.

- `custom objects engine` (module 05) reads the local `CUS_OBJECTS`, an array of `{title, lat, lon, var1, var2, point, fallback, heading}`, creates at most 30 objects named `CUSOBJ1..`, sets `VAR 1`/`VAR 2` (0 when absent), points the object when `point` is not empty (`accident_location`, any location name, or `CUSOBJn`), and uses `fallback` when the title is missing (no fallback, no substitute). Every object is created in its own `try`; the last error text is kept in the local `custom_objects_error`. The old `OBJECT1..15` blocks stay as a compatibility path for scripts written before.
- `accident location pregenerator CUSTOM`: `CUS_USERA` and `CUS_RESCUE` are optional; at 0 the accident location is used.
- `train.json` is regrouped in three edit blocks (mission, advanced options, objects), the object list is one line per object, the old scene (10 objects) is converted.
- `tools/test-custom-script.js` checks the contract statically.

Not done: custom hospital as first proposal, custom audio messages, name of the place instead of the city (111 `:LOCATION` text boxes would have to follow one switch).

## Object pointing: six choices (build 169.89, runtime pending)

Simulator 169.88: `point_object` with a local as subject fails with `unknown locRef`. The subject must be a literal name, so the engine calls `custom object point`, which dispatches on the slot number to `custom point CUSOBJ1..30` (literal subject and targets). Per object the script gives `aim` (0 none, 1 `injured_human`, 2 `injured_human2` and 3 `injured_human3` when `has_object`, 4 `accident_location`, 5 a location `CUSPTn` created from `aimlat`/`aimlon`, 6 the previous object `CUSOBJ(n-1)`). The legacy `point` field is still read ("accident_location" = 4). `CUS_SCRIPT_BUILD` is 169089: older missions ignore `aim`.

## Custom hospital as first proposal (sources 2026-10-30, not built, runtime pending)

The script sets `L:CUS_HOSPITAL LAT/LON` (0 = off) and the local `CUS_HOSPITAL_NAME`. `Query closest hospital` is now a wrapper: with the value set and `MISSION_NUMBER` not 4 (organ transport) it calls `custom hospital first choice` (hospital_user from the coordinates, `hospital_name` = the name, map icon, no query and no comparison with the nearest); otherwise it calls `Query closest hospital default` (the former body, unchanged). All callers (dispatch, `voice hospital proposal`, crew emergency) are unaffected, so the doctor says the custom name (`HOSP.FOUND`) and the user can still change the destination from the menu. Limits: the `hospital_user_Name` token (online submit only) is not set; the organ transport keeps its own query.

## Custom audio messages (design, not implemented)

Spoken text goes through the Companion voice packs, so a script text must not enter a pack. Proposal: the script provides text per event point (for example `CUS_MSG_ARRIVAL`, `CUS_MSG_PATIENT_LOADED`, `CUS_MSG_HOSPITAL`) and the mission speaks it with a reserved key family that the sync tools skip (`voice-texts.js` must be taught to ignore it); the Companion plays it with the voice of the chosen actor. Event points to decide with the user. If the Companion cannot read a text coming from a local, the fallback is a file in the work folder.
