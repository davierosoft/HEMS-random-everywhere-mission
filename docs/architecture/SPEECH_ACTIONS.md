# Speech actions: inventory of the user action buttons and the mission side of the bridge

Status 2026-10-23 (evening): the mission side is implemented in the sources (module `24-speech-bridge.json`,
setting `SPEECH_COMMANDS`, see "Implemented" below). Static tests pass (`tools/test-speech-bridge.js`); nothing was run
in the simulator and the Companion side (push to talk, transport, consent) is not part of this repository. The inventory
below is read from the sources of the working tree (mission 169.68). The machine-readable list of all 58 definitions
is `speech-actions-inventory.json` (macro, module, show condition, what the click sets and calls).

## Implemented in the mission sources (release 169.70)

- Setting `SPEECH_COMMANDS` (`yes` / `no`, default `yes`): first-run default, saved and loaded in the aircraft profiles,
  `no` in the four factory profiles, switch in the tablet Settings (CREW voice options, tab 7) that starts the bridge when
  it is turned on. Off means no thread and no variable written.
- Module `mission-src/macros/24-speech-bridge.json`, GENERATED by `node tools/speech-bridge.js generate`: `speech bridge start`
  (called by `objective1` after the event handlers and by the switch; one running copy), `speech bridge loop` (contract,
  fresh random session, clean mailbox, ready, then a 0.25 s loop: availability refresh and request handling),
  `speech availability`, `speech action run`, `speech availability clear`.
- 14 commands (codes 101-114, list in `tools/speech-bridge.js`, phrases in `tools/speech-phrases.json`): begin_hoisting,
  begin_hoist_up, begin_hoist_dwn, begin_gnd_loading, skid_landing, deciditi, deciditi2, ambuloadlock, hoist_out, hoist_in,
  heli_rescue_here, heli_rescue_back, ambulance_second and ambulance_unload (the click of ambulance_prime, or of
  crew_ambulance_prime when that one is the button that exists). The declaration for the Companion is
  `docs/architecture/speech-contract.json` (generated, `node tools/speech-bridge.js contract`).
- Availability = the button exists (`has_user_action`) AND its `show_condition` holds now. The conditions are copied
  verbatim from the real definitions by the generator; `ambuloadlock` and `ambulance_prime`, which have definitions with
  different conditions, write a tag (`sp_def_<id>`, 1-based) right after each creation and the generated code picks the
  condition of the tag. `node tools/speech-bridge.js check` (part of `test-speech-bridge.js`) fails when a button condition,
  a tag or the module diverges, so the voice can never see a button the pilot cannot click.
- A request: the Companion writes session, command code and, last, the sequence. The mission refuses a wrong session
  (result 2), re-evaluates the condition at that moment (`speech action run`), clicks with `trigger_user_action` (result 1)
  or answers 2, writes the result, then the acknowledgement sequence. Every evaluation sits in a try: a failing read counts
  as not available and never ends the thread.
- Not in this batch: `hoist_power` and `carls_on` (the two switches are not user actions and the equivalence of the CARLS
  variable is unproven), the map dialogs (accept and reject, no voice control by decision), the convenience skips and
  `history`.

Why this exists: the Mission Companion of KeKKERUUU (private repository, branch `dev`, `CLAUDE.md` section
"Coordination with Andrew / Claude: mission speech action bridge") prepared local speech recognition that is
disabled and writes no variable. It waits for a declaration from the mission side: LVAR names, command codes,
phrases per language and the conditions of each action. This document is that declaration in draft, plus the
inventory it is built from. Phrases and names below are proposals until davierosoft approves them.

## Decision of davierosoft, 2026-10-23

The mission executes a spoken action with `trigger_user_action <id>`, the same command the cockpit keypad
already uses. `trigger_user_action` is the equivalent of clicking the user action and has the same limits:
the button has to be visible (statement of davierosoft, not yet measured by a test). No LVAR imitates a
button, no macro is extracted, no id is patched. The Companion side only writes the mailbox and reads the
availability variables; the availability is "the button is visible". Recorded in the Companion `CLAUDE.md` (branch `dev`,
message M024). The owner of the Companion delegated the completion of speech and push to talk to Claude the same
day, so the declaration below is mine to define.

## What a user action is here

- `create_user_action {id, title, show_condition, click_commands}` makes a button at the top of the mission map
  (the user can also bind it to a controller button). `destroy_user_action` removes it. `has_user_action` is 1
  while it exists. `trigger_user_action` clicks it "as if clicked by the user" (HPG documentation).
- The HPG documentation does not describe `show_condition` on a user action, yet the mission uses it on 38 of the
  58 definitions (21 distinct ids). `trigger_user_action` behaves as a click, so an action whose `show_condition`
  is false cannot be fired (owner's statement; test T1 below only confirms it).
- 58 definitions of 34 distinct ids in 7 modules: `05` 30, `10` 13, `09` 9, `11` 2, `12` 2, `03` 1, `13` 1 (module
  `04` only triggers them).
- A gateway from the cockpit already exists: the macro `events creator` (module 04) turns three SDK events into
  `trigger_user_action`, each guarded only by `has_user_action`:
  `H145_SDK_PRIMARY_ACTION_COMMAND`, `H145_SDK_SECONDARY_ACTION_COMMAND` and `{HXX}_SDK_EQUIP_HOIST_ON`.
  Some hoist actions are also triggered by threads after a delay (`delayed threads`).

Things the inventory shows that matter for the design:

1. Nine ids have several definitions and four of them with different conditions: ambulance_prime (7 definitions,
   4 different conditions, two definitions with none), accept_hospital (7, 5 different), ambuloadlock (4, 3
   different) and, with one condition only, accept_user, reject_user, reject_hospital, begin_hoisting,
   skid_landing, ambulance_second. One condition per id cannot describe the first three. Only one definition
   exists at a time, so `trigger_user_action <id>` always reaches the right click, but the availability needs the
   condition of the definition that exists now.
2. Class B (accept and reject) are map dialogs of one place at a time. Decision of davierosoft (2026-10-23): they
   get no voice control, the user is already on the map with the mouse choosing the point.
3. Two commands requested for voice are not user actions: switching the hoist on when the crew asks, and switching
   the CARLS radio on when the crew asks. They need their own mission-side handling (see the word list).

### Single words (owner request 2026-10-23)

A single word is accepted when exactly one visible command carries it. Rule at submit time: the Companion looks at
the `L:HMC_SPEECH_OK_<ID>` of every action that declares the word; exactly one available means run it, none means
refuse, more than one means refuse and give the "which one" cue, never guess. So a wrong action can never run,
the worst case is a refused word. A word may therefore be declared by several actions; the Companion must not
reject a declaration for that.

Which words are practical depends on which buttons can be visible together. From the conditions in the sources:

- Never together, by the numbers: begin_hoisting (height over 30 ft) and skid_landing (height under 25 ft);
  hoist_power (hoist off) and every button that needs the hoist on (begin_hoisting); the pick and drop of the heli
  rescuer (different macros, different phases); ambuloadlock, hoist_in or hoist_out and the ambulance buttons
  (different phases of the patient).
- Always together: deciditi and deciditi2 (same condition), heli_rescue_here and heli_rescue_back, accept and
  reject (not voice controlled). Their words must differ.
- begin_hoist_up or begin_hoist_dwn with begin_hoisting or skid_landing: possible until mission 169.69 when the
  heli rescuer point is inside the landing spot. Since 169.69 the local flag `hr_scene_block` (set when the heli
  rescuer command is created, cleared at its click, destroy, macro start and dispatch reset) hides begin_hoisting
  and skid_landing in that case, so they are never visible together (`tools/test-hr-scene-block.js`, runtime
  pending).
- Possibly together, not proven: skid_landing (collective over 25) with begin_gnd_loading (rotor below the ground
  ops NR, height under 7 ft), unlikely because the rotor is slow in one and loaded in the other. To be confirmed in
  the simulator.

confidence for one-word phrases than for phrases of two or more words (a Companion setting, not a mission one).

Mission-side notes on the two switch commands, both to be tested before they are declared:

- `hoist_power`: the crew asks with the lines "please set the hoist switch on" (pack message `PAX1.86` and its
  variants). The hoist is a kit option; the mission already switches it with the SDK event
  `H:{HXX}_SDK_EQUIP_HOIST_ON` (macro `kit options optimal`). Available while `L:{HXX}_SDK_EQUIP_HOIST` is 0 and
  the crew has asked; the command triggers that event, nothing else.
- `carls_on`: the crew reminds the pilot with `RAD.REM` ("the radio is still off. Switch on the CARLS"). The radio
  rule is powered (battery master or GPCP power switch) and `L:CARLS_CONNECTED` 1 (macro `voice radio ready`).
  What the pilot's own "connect" does on the CARLS, and whether setting `L:CARLS_CONNECTED` to 1 is equivalent,
  is not verified; the mission writes that variable itself in the non-realistic dispatch start. Not available
  without power.

Mission-side behaviour the Companion contract asks for, and how it maps here:

- One thread `speech bridge`, started only when the new setting `SPEECH_COMMANDS` is on (default on, saved in the
  aircraft profiles like every persistent option). It sets READY 0, publishes contract and a fresh session, then
  READY 1; on reload or shutdown it clears READY and every availability variable.
- It reacts to a change of `L:HMC_SPEECH_REQ_SEQ` only: snapshot session and code, refuse a wrong session or an
  unknown code, ignore a repeated sequence, check the visibility at that moment (a click on a hidden button does nothing, the check is what lets the
  mission answer 1 or 2 honestly), call
  `trigger_user_action <id>`, write the result and then the acknowledgement sequence. Result 1 means "clicked",
  not "finished" (a hoist takes minutes).
- A second loop, only while READY is 1, refreshes the availability variables a few times per second. It is the
  only extra cost of the feature and it does nothing when the setting is off.
- Effects are not duplicated: the click of the existing definition runs, the same one as the button and the
  keypad.

## The open design point: where the availability condition lives

The Companion wants `HMC_SPEECH_OK_<ID>` to be 1 only when the action is really permitted, with all visibility
conditions. Today that condition exists only inside each `show_condition`. Two ways:

- Option 1, copy the conditions into an evaluator macro and keep a static test that every copy equals its
  `show_condition`. Cheap and leaves the buttons untouched, but the heterogeneous definitions (point 1 above)
  make a clean copy hard, and a future edit of a button can silently diverge.
- Option 2, one evaluation per action in the availability loop, written to a local flag, and the `show_condition`
  of the button reads that flag. One source of truth for button, keypad and voice, but the buttons would appear
  with the loop period of delay and the core flows (hoist, skid, ambulance) change behaviour: it needs the tests
  below and a decision.

Recommendation: start with class A only and Option 1 for the eleven actions that have one condition only
(begin_hoisting, begin_hoist_up, begin_hoist_dwn, begin_gnd_loading, skid_landing, deciditi, deciditi2, hoist_out,
hoist_in, heli_rescue_here, heli_rescue_back), plus ambulance_second and crew_ambulance_prime, which have no
condition (their availability is `has_user_action`). That is 13 of the 15. ambuloadlock and ambulance_prime, which
have several different conditions, and classes B and C wait for the first result and for tests T1 and T2.
