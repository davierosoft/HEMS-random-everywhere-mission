# Modular mission source rules

- Edit only the module returned by `node tools/mission-workspace.js locate "<macro-or-data-name>"`.
- Keep existing entry order and command spelling. Formatting follows the formatter contract below; do not change semantics while formatting.
- Formatting contract applies recursively to every section, subsection, and API: the title/key and opening delimiter share one line (for example, `"health3": [` or `"health3": {`); never begin a collapsible command section with a standalone `{` or `[`. Short, simple commands—including `set` commands whose complete compact form remains short—stay on one line with all delimiters (for example, `{"set":{"local":"MGsounds_installed"},"value":{"if":{"param":"$FETCH_STATUS"},"eq":200,"then":"OK","else":"NO"}}`). For multiline `if`, `while`, and `for_each` commands, keep the condition and comparison on the opening line, put `then`/`else` or `do` on the next nesting level, place `else` on the same line as the aligned `then` closing delimiter (`],"else": [`), and compact that command's final branch closing as `]}` at the same indentation as its opening command. Each structured command closes its own block on its own aligned line; never merge delimiters belonging to preceding or enclosing commands (for example, do not turn nested `if`/`do`/`while` closures into one `]}]}}` train). Only delimiters belonging to the same command may remain together, such as `]}` for `if`/`while`/`for_each` or `]}}` for `create_thread`. Only genuinely long or structured commands and containers use multiple lines. Each nesting level adds exactly two spaces. Separate sections and subsections with a blank line. In `data`, structured records use one field per line; name and vehicle-name collections may remain compact.
- Between consecutive macro sections, do not insert automatic blank lines; keep one macro per line in the sequence. Use blank lines only for logically distinct data entries or top-level containers.
- For standalone `and`/`or` APIs, put the key and opening `[` on the first line, one operand per following line, and the API closing `]}` on its own aligned line. When `and`/`or` is the condition of `if`, `while`, or `for_each`, use the same multiline operand layout while keeping the final comparison (`eq`, `ne`, etc.) on the header line before `then`/`do`. Do not split `and`/`or` expressions embedded in `set_dispatch` or briefing payloads.
- Run `node tools/check-mission-scope.js snapshot` before the first semantic edit.
- Before each local build, prepare a one-use `node tools/release-workflow.js draft` intent with exact semantic scope. Corrections preserve the supplied revision; use `begin` only for an explicitly requested higher delivery. Draft checks reference the canonical artifact without copying it.
- After editing, run `node tools/mission-workspace.js build`, inspect the artifact diff immediately, then run `node tools/mission-workspace.js check` and `node tools/release-workflow.js static`.
- Prove scope with `node tools/check-mission-scope.js check --strict` and explicit allow flags. Any unlisted root key, macro, or data key is blocking.
- `manifest.json` owns entry order and byte-preserving separators. Do not edit its formatting metadata by hand.
- After intentionally adding, renaming, or removing a top-level macro/data entry, run `node tools/mission-workspace.js reindex` before `build` and inspect both manifest and artifact diffs.
- Never place renderer rows at macro command level. Follow `DEVELOPMENT_RELEASE_CHECKLIST.md` for conditions, persistence, CARLS, medical, vehicle, crew, and release rules.
